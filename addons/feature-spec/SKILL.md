# feature-spec — 기능 설계 명세 워크플로

기능 1개 = 문서 1개(`docs/design/NNNN-slug.md`). 그 문서가 **의도(왜)와 설계(어떻게)를 같이** 들고 있고,
`spec.mjs check` 가 사람 대신 형식·정합성을 본다. 사람은 내용만 본다.

`intent.md` 계열과의 관계, 이 절차를 유지할 근거는 [references/why-tiers.md](references/why-tiers.md).
한 줄로: **intent.md 는 §1~§2 다. 나머지 섹션은 intent.md 가 일부러 안 다루는 영역이라 대체 관계가 아니다.**

## 언제 쓰나

- 새 기능·리팩터를 **착수하기 전** 설계할 때
- 기존 코드에서 **역설계 명세**를 뽑을 때(규제 제출·인수인계)
- 여러 파일·프로세스·비동기 경계를 건드려서 "머릿속 계획"이 안 버틸 때

**안 쓰는 경우**: 파일 1개 수정, 오타·문구, 이미 명세가 있는 항목의 후속 커밋.
작은 일에 tier L 을 붙이는 게 이 절차가 욕먹는 유일한 이유다.

## 0. tier 부터 정한다 (제일 중요)

| tier | 쓸 때 | 필수 섹션 |
|---|---|---|
| **S** | 파일 2~3개, 상태 기계 없음, 외부 경계 없음 | §1 의도 · §2 수용기준 · §3 확정사실 · §9 변경지점 · §10 잠재문제 · §11 착수순서 |
| **M** | 기본값. UI 상태가 생기거나 파이프라인이 여러 단계 | S + §4 유스케이스 · §5 flowchart · §6 상태전이 |
| **L** | 규제(SaMD/SDD/RMF), 외부 인터페이스, 동시성·타임아웃·스키마 변경 | M + §7 타이밍 · §8 ER · §12 추적성 |

**모호하면 M.** 다이어그램을 하나 더 그리는 비용보다, 상태 전이를 안 그려서 실패 경로에 잔여물 남기는
비용이 크다. 반대로 tier L 을 습관적으로 붙이면 문서가 의례가 되고 아무도 안 읽는다.

## 절차

### 1) 문서를 만든다
```
node "<skill_dir>/spec.mjs" new "<제목>" --tier M --issue <Gitea 이슈번호>
```
`docs/design/0007-slug.md` 가 생기고 tier 에 맞는 섹션만 채워진다.

### 2) §1 의도 · §2 수용기준을 **사용자와 합의한다**
여기서 코드로 넘어가지 않는다. 확정 전까지는 질문이 코드보다 싸다.
- §1 불변식: 절대 깨지 않을 것(원본 불변, 비밀은 프로세스를 안 떠남, 개인정보 최소).
- §1 비목표: 이번에 **안 하는 것**을 적어야 스코프가 안 샌다.
- §2 수용기준: `AC-n` 마다 **검증 방법**을 반드시 적는다 — 비어 있으면 `check` 가 막는다.
  "빠르다" 금지. `p95 < 200ms`, `실패 시 artifacts 행 0건` 처럼 관측 가능하게.

### 3) §3 확정 사실을 조사로 채운다 (추측 금지)
버전·기존 동작·의존성 유무를 **실제로 확인해서** 적는다. "어떻게 확인했는지"까지 한 칸에.
확인 못 한 가정은 §3 이 아니라 **§10 잠재 문제**로 내려보낸다. 이 구분이 이 문서 포맷의 핵심이다.

### 4) 다이어그램을 그린다 (tier 가 요구하는 것만)
| 섹션 | 다이어그램 | 이걸로 잡는 실수 |
|---|---|---|
| §4 유스케이스 | `flowchart LR` | 누가 쓰는지, 예외 시나리오 누락 |
| §5 파이프라인 | `flowchart TD` | 분기·에러 경로 누락 |
| §6 액션·상태 전이 | `stateDiagram-v2` | **실패 상태에서 잔여물 정리 누락** — 가장 자주 터지는 곳 |
| §7 타이밍 | `sequenceDiagram` | timeout 값의 근거 없음, 순서 뒤집힘 |
| §8 데이터 | `erDiagram` | 마이그레이션·CASCADE 누락 |

§6 은 표로 상태별 저장/이벤트/UI 반응까지 같이 적는다. 그림만 있으면 반쪽이다.

### 5) §9 변경 지점 · §11 착수 순서
- §9 경로는 백틱으로. 신규 파일은 `(신규)` 표기 — `check` 가 실존 여부를 대조한다.
- §11 은 **얇은 수직 슬라이스**로 자른다: "버튼 하나가 실제로 되는" 단위. 각 항목에 담당 `AC-n` 을 적는다.

### 6) 검증하고 사람에게 보인다
```
node "<skill_dir>/spec.mjs" check
node "<skill_dir>/spec.mjs" render          # 다이어그램 -> .mmd/.png (육안 컨펌용)
```
`check` 가 통과하면 `status: approved` 로 올리고 **여기서 사용자 승인을 받는다.** 승인 전 구현 금지.

### 7) 구현 — 슬라이스마다
슬라이스 하나 끝날 때마다 §11 체크박스를 `[x]` 로 바꾸고 커밋한다.
설계가 틀린 걸 발견하면 **코드가 아니라 문서를 먼저 고친다**(§3 에 새 확정사실 추가 → 설계 반영).
문서를 안 고치고 코드만 비켜가면 다음 사람이 문서를 안 믿게 되고, 그때부터 이 절차는 순수 비용이다.

### 8) 종료
`status: done` 으로 올린다. §11 이 다 안 닫혔으면 `check` 가 막는다.
tier L 이면 §12 추적성(AC ↔ 커밋 ↔ 테스트 ↔ 위험)을 채운다 — 이게 SDD/RMF 로 그대로 나간다.

## CLI

```
node "<skill_dir>/spec.mjs" <명령> [옵션]
```

| 명령 | 하는 일 |
|---|---|
| `new "<제목>" [--tier S\|M\|L] [--issue N] [--slug s]` | tier 에 맞는 명세 골격 생성 |
| `check [<명세>]` | 형식·정합성 검사. 오류 있으면 exit 1 |
| `status` | `docs/design` 전체의 tier·status·진행률·AC 수 |
| `render [<명세>] [--out DIR]` | mermaid 블록을 `.mmd` 로 추출, `mmdc` 있으면 `.png` 까지 |

공통 옵션 `--repo <경로>` (기본: 현재 디렉터리의 git 루트).
`<명세>`는 경로·id·부분 문자열 아무거나. 명세가 1개면 생략 가능.

`check` 가 잡는 것: tier 별 필수 섹션 누락 / 빈 섹션 / 요구 다이어그램 종류 불일치 /
`AC-n` 중복·검증방법 누락 / **§11 이 안 맡은 고아 AC** / §9 의 실재하지 않는 경로 /
`status=done` 인데 미완료 항목 / 미치환 `{{...}}` 플레이스홀더 / TBD 잔존.

템플릿의 빈칸은 전부 `{{...}}` 로 표시된다 — 지우거나 채우면 경고가 사라진다.
`(신규)` 로 적힌 파일이 이미 존재한다는 경고는 `draft`·`approved` 단계에서만 뜬다
(구현이 시작되면 존재하는 게 정상이라).

## 유의사항 — 이 절차가 실패하는 방식

1. **tier 인플레이션.** 전부 L 로 쓰면 아무도 안 읽는다. S 를 실제로 쓸 것.
2. **문서와 코드의 분기.** 설계 변경 시 문서를 먼저 고치지 않으면 문서는 즉시 거짓말이 된다.
   `check` 는 형식만 본다 — 내용의 진위는 사람 몫이다.
3. **다이어그램 미화.** 예쁜 그림이 목적이 아니다. §6 의 실패 경로처럼 **틀리면 아픈 것**만 그린다.
4. **§3 오염.** 확인 안 한 걸 확정 사실에 적으면 문서 전체의 신뢰가 죽는다. 의심스러우면 §10.
5. **AC 없는 착수.** 검증 방법이 없는 수용 기준은 구현이 끝났는지 판정할 수 없다.

## 핵심 원칙 한 줄

> 의도는 사람이 정하고, 설계는 다이어그램이 강제로 드러내고, 형식은 `check` 가 보고,
> 진위는 육안 컨펌이 본다. 이 넷이 다 있어야 "계획대로 만들었다"를 증명할 수 있다.
