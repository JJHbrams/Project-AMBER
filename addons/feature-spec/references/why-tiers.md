# 왜 이 절차를 유지하는가 — intent.md 와의 관계

## 질문

"사용자기획 → 기능명세 → flowchart / action diagram / timing diagram / 유스케이스 시나리오 분석 →
계획 기반 구현" 이 일련의 과정을, Claude 진영의 `intent.md` 방식과 비교했을 때 계속 고수할 필요가 있나?

## 답: 대체 관계가 아니다. 층이 다르다.

`intent.md` 는 **무엇을·왜·어떤 제약으로** 만드는지를 코드보다 먼저 커밋해 두는 짧은 문서다.
Anthropic 의 AI-Native SDLC 가이드도 `CLAUDE.md`(어떻게 일하는가)와 `INTENT.md`(무엇을 만드는가)를
역할로 나눈다. 즉 intent.md 가 커버하는 건 우리 문서의 **§1 의도 · §2 수용기준**까지다.

intent.md 가 **일부러 안 다루는 것**이 그 아래다:

| 우리 섹션 | intent.md 가 안 다루는 이유 | 안 그리면 실제로 터지는 것 |
|---|---|---|
| §3 확정 사실 | intent 는 "무엇"이지 "환경 조사"가 아니다 | 에이전트가 없는 의존성을 있다고 가정하고 설계 |
| §5 파이프라인 | 구현 자유도를 남기려고 의도적으로 비움 | 에러 분기 누락 |
| §6 상태 전이 | 위와 동일 | **실패 상태 잔여물** — LLM 계획이 가장 자주 빠뜨리는 곳 |
| §7 타이밍 | 위와 동일 | timeout 값에 근거가 없음 |
| §12 추적성 | 규제 산출물은 범위 밖 | SDD/RMF 제출 시 근거 재구성 불가 |

## 그래서 유지 근거 3가지

**1. 규제.** `TruviewCADMOM-Standalone/docs/200_dev/` 에 이미 소프트웨어 설계 명세서(SDD)와
위험관리파일(RMF)이 있다. SaMD 는 설계 근거와 위험 통제의 **추적 가능한 기록**을 요구한다.
intent.md 한 장으로는 이 의무를 못 채운다. 이건 취향이 아니라 요건이다.

**2. LLM 이 실제로 틀리는 지점이 다이어그램 층에 있다.** 산문 계획은 그럴듯한데 상태 전이표를
채우게 하면 "Failed 에서 선점 행을 어떻게 지우나"가 빈칸으로 드러난다. mermaid 는 생성 비용이
거의 0 인데(텍스트다) 강제로 분기·순서·종료 상태를 **열거하게** 만든다. 비용 대비 검출률이 좋다.

**3. 육안 컨펌 표면.** 사람이 코드 diff 를 읽고 설계 오류를 잡는 것보다, flowchart 하나 보고
"여기 실패 경로 없는데?" 하는 게 훨씬 싸고 빠르다. 승인 지점이 문서에 있어야 한다.

## 그런데 고쳐야 할 것 — 계층화

기존 방식의 진짜 약점은 **내용이 아니라 균일한 무게**다. 오타 수정에도 유스케이스·타이밍
다이어그램을 요구하면 절차가 의례가 되고, 의례가 되면 사람들이 문서를 사후에 급조한다.
그 순간 문서는 설계 근거가 아니라 알리바이가 된다.

그래서 tier S/M/L 로 나눴다. 그리고 intent.md 의 좋은 점 — **의도를 코드보다 먼저,
버전관리 안에, 짧게** — 을 §1·§2 로 흡수했다. 버리는 게 아니라 앞단에 붙였다.

## 형식 검사를 기계에 넘긴 이유

사람이 리뷰에서 "AC 검증방법 비었네", "이 경로 이제 없는데" 를 지적하는 건 낭비다.
`spec.mjs check` 가 보는 것은 전부 **판정이 결정적인 것들**이다:

- tier 별 필수 섹션 유무 / 빈 섹션
- 요구 다이어그램 종류 일치 (§6 에 flowchart 를 그려놓는 실수)
- `AC-n` 중복·검증방법 공란
- **고아 AC** — §2 에 있는데 §11 착수 순서에서 아무도 안 맡은 것
- §9 변경 지점 경로의 실존 (`(신규)` 표기 예외)
- `status: done` 인데 미완료 체크박스

내용의 진위는 여전히 사람 몫이다. 기계는 사람이 내용에만 집중하도록 형식을 치운다.
